Stargazing Dashboard

Local route /interactive-explanation/stargazing-dashboard/ is an original Engineering Sandbox lab that builds a first-person topocentric sky dome. It provides a time and location engine, bundled star/constellation/meteor data, ephemeris-style planet positions, guided target navigation, and a telemetry HUD overlay. Wave 1 freezes the page contracts only; the canvas, state store, controls, catalog hooks, scene adapter, and HUD adapter are safe placeholders so later waves can add astronomy without changing public ids or script order.

Source snapshot

This route does not mirror one published external article. It is a local original build created for the interactive-explanation collection and written specifically as a first-person stargazing dashboard.

  • The route uses neutral provenance handling because there is no single upstream article to reference.
  • The shell is the shared Engineering Sandbox lab variant for hero framing and metadata attribution.
  • Astronomy calculations follow standard low-precision algorithms based on Jean Meeus Astronomical Algorithms for Julian date, GMST/LST, equatorial-to-horizontal transforms, and sun/moon/planet positions.
  • Bright star positions come from a HYG/Yale-derived local subset bundled as route-local JSON data.
  • Constellation boundary figures and meteor shower data are authored from public reference knowledge into route-local JSON schemas.
  • Three.js r70 is vendored locally at ../ev/scripts/three.js and loaded before route scripts.
  • Wave 1 freezes the public API shape of each module (state, astro, catalog, controls, scene, hud) but returns placeholders only; real rendering and ephemeris computation land in later waves.

Asset handoff

  • stargazing-dashboard/index.html owns the route shell, hero, observation deck, dashboard grid, HUD panels, and control bench.
  • stargazing-dashboard/css/stargazing.css provides the dark night-sky theme, dashboard layout, panel styling, and responsive breakpoints.
  • stargazing-dashboard/js/astro.js defines the astronomy API surface: julianDate, gmstHours, lstHours, equatorialToHorizontal, sunPosition, moonPosition, planetPosition (Wave 1: placeholders).
  • stargazing-dashboard/js/state.js provides the frozen state store: getState, setState, subscribe, advanceTime with observer, time, toggles, weather, selectedTargetId, and look shapes.
  • stargazing-dashboard/js/catalog.js defines lazy async catalog loaders for stars, constellations, and meteor showers from local JSON paths.
  • stargazing-dashboard/js/controls.js implements pointer-drag and keyboard look controls that write azimuth and altitude into the state store.
  • stargazing-dashboard/js/scene.js defines the Three.js scene lifecycle (createScene with start/stop/resize). Wave 1: no-op adapter.
  • stargazing-dashboard/js/hud.js binds DOM controls (location, time, weather, toggles) to the state store and returns an update handle.
  • stargazing-dashboard/js/main.js bootstraps the route: WebGL guard, fallback display, adapter wiring, and ready-state signaling.
  • ../ev/scripts/three.js is a vendored copy of Three.js r70 loaded as a global script before route-local modules.
  • ../shared/engineering-sandbox.css and ../shared/engineering-sandbox.js provide the shared lab shell.
  • ../shared/public-footer.css and ../shared/public-footer.js provide the provenance footer.
  • Future data files expected at ./data/stars.json, ./data/constellations.json, ./data/meteor-showers.json.

Known deviations

  • Neutral provenance: there is no referenceUrl because this is an original local route, not an upstream replica. The footer is wired with data-reference-mode="neutral" and a provenance note.
  • Astronomy accuracy is naked-eye visual grade, not ephemeris-grade. Positions are sufficient for identifying bright stars, planets, and constellations by eye but are not suitable for telescope pointing or precise astrometry.
  • The weather panel is a sandbox with sliders (cloud cover, seeing, light pollution). It is not connected to a live weather API. Values feed the state store for future rendering use.
  • Three.js r70 is an older stable version chosen for compatibility. It provides basic WebGLRenderer, PerspectiveCamera, Scene, and SphereGeometry. Later waves may require upgrading or adding supplemental modules.
  • Wave 1 is a contract freeze: all module APIs are defined and wired, but astronomy functions return zeros/null and the scene adapter is a no-op. Smoke checks verify the DOM contract and ready state, not the rendered sky.

Validation guidance

  • Keep the route self-contained and subpath-safe; all assets must remain local to stargazing-dashboard/ or the shared shell paths (../shared/, ../ev/).
  • Run node tools/sync-route-metadata.mjs . after any manifest changes to keep pages.json in sync.
  • Run node tools/check-public-surface.mjs . after any content or structural changes to the route or docs.
  • Run node tools/smoke-bundle.mjs . --route stargazing-dashboard for route-specific smoke testing (desktop/mobile overflow, footer, console errors, ready-state dataset).
  • Validate JS syntax: node --check stargazing-dashboard/js/main.js (and each module under js/).
  • Validate JSON data files (when added) with node -e "JSON.parse(require('fs').readFileSync('stargazing-dashboard/data/stars.json','utf8'))".
  • The route body sets data-story-shell="engineering-sandbox" and data-story-variant="lab". Do not switch to the longform essay variant without updating the hero layout, navigation, and chapter expectations.
  • Parity entries for Wave 1 modules that are still placeholders should remain marked honestly (e.g. "not yet verified" or "Wave 1 contract only") rather than claiming false PASS.
